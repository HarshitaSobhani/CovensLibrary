# Threat model — Coven's Library

Assets: member personal data (names, phone numbers, e-mail), the financial and token ledger (immutable), loan history, the audit trail, the encrypted backups and their key, the Google Drive authorisation, the owner's login. One owner, one Windows 11 computer (the Dell), no member accounts, application bound to `127.0.0.1`.

Trust boundaries: (1) browser ↔ server on loopback; (2) Django process ↔ PostgreSQL as the **runtime** role `coven_app`; (3) owner role `coven_owner` (migrations, grants, restores) used only deliberately; (4) Windows Credential Manager (per-user DPAPI) for secrets; (5) Google Drive for encrypted backups.

Evidence: `docs/SECURITY_AUDIT.md`. "Residual" is what remains **after** the controls; nothing here promises zero data leakage.

## 1. The thirteen scenarios

| # | Scenario | What becomes accessible | Controls (verified) | Residual risk |
|---|---|---|---|---|
| 1 | Unauthenticated attacker reaches the application | Only the login, reset and recover pages and `/healthz/` (`{"app","status"}`) | every route requires login (swept ×4 methods); CSRF; throttle 5/15 min with no lockout and no enumeration; reset limited to 3/15 min | Reachable only from this computer (loopback + Host check). Another local program or Windows user can open the login page and guess passwords at the throttled rate |
| 2 | A normal authenticated request bypasses owner authorization | Nothing extra: there is exactly one account and no roles | login required everywhere; server-side validation of every financial rule; hidden buttons are not relied on | If a second account were ever created it would have full access (single-owner test guards this) |
| 3 | Exploit of a Django view or a dependency | Whatever the Django process can do: all data, and the runtime role's operations | XSS/SQL/CSRF/redirect probes negative; CSP blocks injected scripts; dependencies pinned with hashes and audited | A new vulnerability in Django, waitress or a library is possible; `pip-audit` covers only *known* ones. **If Django itself is compromised the attacker can read everything it can read and use the Credential Manager entries of the signed-in account** |
| 4 | Attacker obtains the runtime database credentials (`coven_app`) | Read every table (members, ledger, audit, session ids); write to mutable tables; log in as the owner by editing the password hash or reusing a session id | The role is not a superuser, owns nothing, cannot read server files, run programs, alter roles or schema, remove triggers, or change/delete financial, token, loan, audit or backup history (attacked from this role). Password now stored in Credential Manager, not plain text | Confidentiality of all data is lost; the application is effectively controllable. History cannot be rewritten, so the evidence stays |
| 5 | Attacker obtains the Windows owner account | Everything: the application, the database password, the backup key and Google token (same account), saved browser sessions | Nothing in the application defends against the account that owns the secrets. Recommend a strong Windows password, no shared use, screen lock | Total. Use the incident procedure and restore from a backup |
| 6 | Attacker reads the database files directly (stolen disk, copied data folder) | All records in plain text, unless the volume is encrypted | **BitLocker is mandatory (decision S-05)**: an administrator's standalone `Verify-BitLocker-Admin.ps1` must pass (off, unavailable or still encrypting writes no record) and the owner's non-elevated Setup then requires that record; its recovery key must be kept off the computer; DPAPI-protected secrets cannot be opened offline without the Windows account. **Unverified on the Dell** | If BitLocker is defeated or the machine is stolen while unlocked/running: total loss of confidentiality. No application-level encryption (decision S-03), so nothing further protects the fields (section 3) |
| 7 | Attacker obtains a backup file | Nothing readable without the key: AES-256-GCM, authenticated, SHA-256 verified | Key only in Credential Manager; recovery key kept on paper off the computer; tamper/truncation/splice/reorder detected; **safe key rotation exists (S-04)** so a suspected key can be replaced for new backups | A leaked key opens every backup made with it until those backups age out (rotation does not re-encrypt old ones). Earlier backups keep data of members anonymised later |
| 8 | Attacker obtains Google Drive OAuth credentials | Read the (encrypted) backup files in the app folder; upload or delete files there (`drive.file` scope: only files the app created) | Token in Credential Manager; scope limited; uploads verified by size and SHA-256; retention keeps 30 daily + 12 monthly | Backups could be deleted (availability); encrypted content stays protected. Revoke at the Google account |
| 9 | Attacker modifies or deletes backups | Modified file: restore refuses it (authentication fails). Deleted file: that backup is gone | AES-GCM + manifest hashes; Drive trash/version history; `backup_status` and the dashboard warn after 26 h | Deleting all backups cannot be prevented from the Google account side |
| 10 | Attacker reads logs or browser caches | Logs: scrubbed (no passwords, tokens, addresses, phone numbers, DB values); browser: authenticated pages are `no-store`; local storage holds only the theme | `core/safelog.py`; headers; protected log folder | Downloaded receipts/exports in the Downloads folder and browser history (search terms) remain on the PC |
| 11 | Malicious uploaded file | The only upload is the spreadsheet import (5 MB) | magic bytes + zip bounds + row/column limits; XXE and entity bombs inert; never executed; not stored under a user-controlled name | A new parser flaw in `openpyxl` would be reachable by the owner only |
| 12 | Attempt to modify immutable financial records | Nothing: UPDATE/DELETE/TRUNCATE and trigger changes are denied to the runtime role; the owner role is also bound by the triggers | privileges **and** triggers; corrections are separate reversal/adjustment records | A holder of the **owner** credentials or `postgres` can drop triggers (break-glass by design); keep `.env.owner` deleted after upgrades |
| 13 | Access from another device or network | None: the server listens on 127.0.0.1 only; other Host headers get 400 | `serve_local` refuses other hosts; `coven.E010`; the listening socket read from the kernel in a test | A local port-forwarding tool or reverse proxy set up by someone with the Windows account could expose it; nothing prevents that |

## 2. Data-flow summary (what leaves the computer)

E-mail (SMTP) for notices and reset links; encrypted backups to Google Drive; WhatsApp links are opened by the owner and sent by her; nothing else. No analytics, no remote fonts or scripts (CSP forbids them).

## 3. Encryption and key custody — each item investigated

For every item: where the key lives and whether a compromised Django process can use it.

| # | Topic | What it protects | Key location | Can a compromised Django process reach the key? | Operations, recovery, failure modes |
|---|---|---|---|---|---|
| 1 | **BitLocker** / device encryption | Disk theft (database files, logs, `app.env`, local backups, temp files) | TPM (+ Microsoft-account or printed recovery key) | Yes, while the computer is unlocked and running (the volume is transparent to Windows) | Needs Windows 11 Pro (BitLocker) or Home with device encryption. **Keep the recovery key off the computer**; losing it and the TPM state locks the disk. Recommended first step. **Unverified**; `verify_runtime.ps1` shows the status (needs administrator) |
| 2 | **Application-level field encryption** (phones, e-mails, notes) — **decided: not introduced at this stage (S-03)** | Would protect a reader of the database or of a plain dump who does **not** control the Django process | Would be the Credential Manager of the owner's account | **Yes.** Django must decrypt to show a member, search, send a notice or print a report, so it would *not* protect against a compromised Django process or the Windows account | Costs if ever approved: search by name/phone and the strict-phone logic stop working on ciphertext (blind indexes); every report and export path changes; backups and restores must carry the key; key loss makes members unreadable; in-place encryption of existing rows needs an approved migration and a rehearsed restore. **Residual risk accepted:** whoever can read the database — through the runtime password, a copied data folder or an unlocked stolen computer — reads every personal field in clear text; BitLocker (S-05) is the only control for the offline case |
| 3 | Key storage outside source and database | Secrets never in Git or in the database | Backup keys (working, pending, retired): Credential Manager. Runtime secrets: Credential Manager, **the only source in production (S-02): no environment or file fallback; plaintext variables are refused; an unreadable store stops the application** | Yes (same account) | `store_secrets.py` and `connect_drive` never replace an existing secret without `--replace`; no key or secret is ever generated or substituted silently; the launcher never creates a key |
| 4 | **Windows Credential Manager** | Offline reading; other Windows users | DPAPI key derived from the signed-in user's logon secret | Yes, as that user | **If an administrator resets the Windows password** (instead of the user changing it), the DPAPI-protected entries become unreadable: the backup key and runtime secrets are lost. Keep the recovery key and the runtime passwords written down off the computer. A profile rebuild has the same effect. **Unverified on the Dell** |
| 5 | Backup encryption and recovery key | Backups at rest and in Drive | Working key in Credential Manager; recovery key = the same key on paper (one paper key per key: current and retired) | **Yes** (it must create backups). It can therefore also decrypt any backup it can download | **Rotation implemented (S-04):** `docs/KEY_ROTATION_AND_RECOVERY.md`. If a paper key is lost together with the computer, the backups made with that key cannot be opened |
| 6 | Google Drive OAuth token | Access to the backup folder | Refresh token + client secret in Credential Manager | Yes | `drive.file` scope; revoke under the Google account's third-party access. Tokens are never logged (scrubbing; SEC-05) |
| 7 | Temporary files | — | — | — | The archive is assembled in a per-run temporary folder, **including a plaintext database dump for a short time**; it is removed on success and on every failure path (tests). On NTFS the deleted blocks are not wiped: BitLocker is the mitigation. A restore also decrypts to a temporary folder |
| 8 | Logs and diagnostics | — | — | — | Scrubbed before writing (SEC-04); 2 MB × 5 rotation; the folder is private to the owner account |
| 9 | Browser cache and local storage | — | — | — | Authenticated pages `no-store`; local storage holds only the theme choice; the session cookie is HttpOnly and ends at midnight. Search terms appear in browser history |
| 10 | Exported reports and receipts | — | — | — | Downloads are `no-store` and audited (counts, not content); they contain personal data (masked for anonymised members) and sit in the browser's Downloads folder until deleted |

**Separate security boundary?** Nothing sensitive can be moved out of reach of the Django process without breaking a feature the owner uses daily. What *is* separated: the owner database role (never in the runtime environment), the runtime password (Credential Manager, not a file), and the recovery key (paper). A truly separate boundary (a second Windows account running a signing/decryption service) would add a service, a key-management story and failure modes; it is not recommended for a one-computer library. No new key-management service or encryption scheme was introduced.

## 4. Accepted residual risks (summary)

Same-account compromise; compromise of Django itself; BitLocker defeated or the machine stolen while running; old backups stay readable with an exposed old key until retention removes them (rotation protects new backups); no field-level encryption (S-03); plain HTTP on loopback; the `unsafe-inline` style allowance; downloaded files and browser history; Windows-specific behaviour unverified until the Dell is tested.
