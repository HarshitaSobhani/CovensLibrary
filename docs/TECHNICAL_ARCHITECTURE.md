# TECHNICAL ARCHITECTURE — Coven's Library

Status: specification for approval; nothing implemented. Versions to be verified and pinned at Phase 1. Business rules: `OPEN_QUESTIONS.md` §1 (authoritative); data model: `docs/ERD.md`.

## 1. Principles
Modular monolith. One PostgreSQL database. Server-rendered Django Templates + HTMX. Business rules live in service functions backed by DB constraints. No React, microservices, Redis or Celery; Docker is not required.

## 2. Stack and environments
Python 3.12 · Django 5.2 LTS (re-check support window at Phase 1) · PostgreSQL (same major version on dev, runtime, any future cloud) · Django Templates + HTMX · Bootstrap 5 + CSS variables · Chart.js. Custom user model from the start; single owner, no signup route. Database access uses two roles (§18).

| Environment | Machine | Notes |
|---|---|---|
| Development | MacBook M3, macOS | developer tooling; documented separately |
| Runtime | Dell, **Windows 11** (edition/build unspecified until verified) | localhost-only; Task Scheduler; `waitress`; PowerShell |

Application code stays OS-neutral (no hard-coded paths); all machine-specific settings via environment variables, so a later cloud move is a configuration change. Timezone `Asia/Kolkata` for every date, timestamp, calculation, schedule, backup and audit event.

## 4. Service layer
`<app>/services/*.py`; each operation `@transaction.atomic`, locks rows (`select_for_update`), raises typed `RuleViolation`, calls `audit.record()`. Views are thin.

**Date policy (`memberships/policy.py`, the only place date arithmetic lives)** — pure functions with `today` injected:
- `expires_on` = start + N calendar months, day clamped to the target month's last day (31 Aug 2026+6 → 28 Feb 2027; 31 Jan 2027+1 → 28 Feb 2027; 29 Feb 2028+12 → 28 Feb 2029). Start inclusive.
- `last_valid_day = expires_on − 1`. Expired from `expires_on`.
- `max_due_date = last_valid_day` (issue and renewal). First expired day never valid.
- `issue_blocked_from = last_valid_day − 15` (10 May → 25 April). Independent of `max_due_date`; both checked.
- Renewal rejected if `today > due_on` or new due date > `max_due_date`.
- Grace end = `due_on + 7` (live setting); day 8 = `due_on + 8`.
- Early renewal starts at the current subscription's `expires_on`; late renewal at the owner-entered activation date; at most one scheduled subscription.

## 5. Rule enforcement map
| Rule | Service | DB backstop |
|---|---|---|
| one active loan per member/copy | `issue_loan` | partial unique indexes |
| no subscription overlap | `create_subscription` | exclusion constraint |
| one scheduled subscription max | `register_member` / `renew_subscription` (member lock, `policy.next_start`) | — |
| fully paid before activation | single atomic registration/renewal txn | transaction rows created settled |
| fees non-refundable | no fee-refund service/kind exists | CHECK on `kind` enum |
| token once per cycle; no double refund/forfeit | `collect_token`, `refund_token`, `forfeit_token` | partial unique per cycle |
| renewal and new borrowing blocked while current token cycle is forfeited (subscription stays valid); fresh token = new cycle | `renew_subscription`, `issue_loan`, `start_new_token_cycle` | — |
| Good + Available issuable; Poor ⇒ Withdrawn | `issue_loan`, return service | CHECKs on copy |
| reversal not deletion | `reverse_transaction` | append-only triggers, UK `reverses_id` |

## 6. Identifiers and numbering
Formats: member `COV-M-000001`; copy `COV-C-000001` (barcode value = copy ID); internal transaction ID = UUID for every financial transaction; four separate receipt sequences, each numbered per year: `SUB-YYYY-000001` (subscription), `TOK-YYYY-000001` (token collection), `REF-YYYY-000001` (token refund), `ADJ-YYYY-000001` (adjustment). Forfeitures and reversals carry a UUID only. A combined registration printout lists both the subscription and token-collection receipts. Sequences come from `ID_SEQUENCE` keyed by (name, year) with row lock inside the creating transaction (gaps on rollback acceptable, duplicates impossible). `YYYY` is the **calendar year (Jan–Dec, Asia/Kolkata) of the receipt issuance date**; a backdated payment/effective date never changes it (e.g. effective 31 Dec 2026, issued 5 Jan 2027 → `SUB-2027-…`). The sequence is keyed by (name, year) using the issuance year.

## 7. Scheduled automation (no Celery)
One idempotent management command (`run_daily_jobs`, implemented in Phase 4b with the day-8 forfeitures), run daily at the configured time by **Windows Task Scheduler** on the Dell and also at application launch (catch-up). It performs, in order: overdue day-8 forfeitures, automatic emails, backup (and the 26-hour health check). Idempotency by unique constraints (one forfeiture per token cycle, `dedupe_key` per notification).
- **Day 8 forfeiture:** loan with `today ≥ due_on + 8` and still unreturned → automatic full forfeiture, `owner_confirmed=false`, `effective_date = due_on + 8`, `processed_at = now`. If the Dell was off, the next launch processes it with the **original effective date**. A return recorded on day 8 still results in forfeiture.
- **Grace-setting changes:** saving a new `grace_days` records `SettingChangeEvent`, computes loans that become newly eligible, and creates `PendingForfeiture` rows; each requires owner confirmation before any ledger entry. Normal day-8 processing is not affected. If the owner **declines**, nothing is posted; a mandatory reason and audit record are stored; the owner is not prompted again for that event and the daily job skips the loan's declined event.
- **Owner-confirmed forfeitures:** Damaged, Poor and Lost returns post only after explicit owner confirmation with a mandatory reason; Poor sets condition `Poor` and status `Withdrawn`, Damaged sets status Damaged; the copy leaves circulation; Lost closes the loan as Lost. A later-recovered lost book never auto-reverses; correction requires a separate owner-approved adjustment.
- **Backdating:** any past date with mandatory reason and audit; financial effects need additional owner confirmation; event date, effective date and `processed_at` stored separately.

## 8. Backup and replacement-computer recovery
**Pipeline:** `pg_dump -Fc` → archive with `media/` + manifest (app version, PostgreSQL version, migration list, timestamp, key fingerprint) → **AES-256-GCM** (chunked) → **SHA-256** → upload to the owner-selected Google Drive folder (`drive.file` scope) → verify upload (size/hash) → `BackupRun` → retention (30 daily, 12 monthly independently; monthly = promoted copy; never delete the newest successful backup; dry-run and fake-clock tests).
**Schedule/health:** daily at fixed time; catch-up at next launch; dashboard warns if last success > 26 h; failures shown.
**Key custody:** the key is randomly generated. On the Dell the working key is stored in **Windows Credential Manager** (protected by the Windows user account); never in the repo, database, backups or the Drive folder. The owner saves a separate **recovery key**; it is never stored with backups. Losing the recovery key may make backups unrecoverable and the owner is told so. Credential Manager entries are **not** assumed to transfer between computers.
**Restore (CLI-first):** `manage.py restore_backup` with typed confirmation and a pre-restore backup. Replacement-computer procedure:
1. Install prerequisites (Python, PostgreSQL, application code) on the replacement Windows computer.
2. Re-authorise Google Drive (fresh OAuth consent) and obtain the encrypted backup.
3. Obtain the separately stored recovery key.
4. Owner explicitly confirms key restoration.
5. Restore the working key into Windows Credential Manager from the recovery key.
6. Verify key access (fingerprint matches manifest).
7. Verify backup integrity (SHA-256).
8. Restore database and media.
9. Check PostgreSQL/application/migration compatibility; run migrations if required.
10. Verify data relationships and application functionality.
Recovery is **not** claimed verified until this has been rehearsed on a clean machine.

## 10. Authentication
Owner only. Django password hashing. Email-based password reset; when SMTP is unavailable, local CLI recovery with a recovery code that is single-use, stored hashed, displayed once and expires after 15 minutes. The owner authenticates at least daily; sessions expire at end of day (`Asia/Kolkata`); **unlimited logins per day** (logout, lost or expired sessions never block another login). Failed logins are audit-logged; **rate limiting** applies after **5 failures within 15 minutes** (throttled until the window expires; success resets the counter). **No account lockout.** The limiter is database-backed and concurrency-safe: check, authentication and recording run in one transaction under PostgreSQL advisory locks keyed by the identifier hash and client address, so simultaneous requests cannot exceed the limit.
**Identifiers are never stored as typed.** A username is persisted only if it matches a real account; otherwise only an HMAC key (for throttling) is kept, so a password typed into the username box never reaches `LoginEvent` or the audit log.
**Password reset.** Email link (Django token, single use). Lifetime: **3,600 seconds (1 hour), decided by the owner** (Django's default would be 3 days); set explicitly in `PASSWORD_RESET_TIMEOUT`, tested at both sides of the boundary. An expired or already-used link shows the same generic "invalid or has expired" page as an unknown link, and cannot change the password. Requests and completions are audited (never the address, token or link). Throttle (implementation default, not an approved number): at most **3 reset requests per 15 minutes** per email key and per client address; a throttled request gets the same generic response and sends no email.
**Single owner.** The `accounts_single_owner` database constraint allows only one account; `manage.py create_owner` is the supported way to create it (refuses if one exists).
**Audit redaction.** Keys (password, secret, api_key, otp, recovery_code, code_hash, passphrase, token, reset_token, authorization, key, session and variants, recursively) and credential-shaped values (bearer/JWT strings, `key=value` pairs, reset URLs, recovery codes, long opaque tokens) are redacted before anything is written; ordinary business data and the refundable-token fields (`token_cycle`, …) are preserved.

## 11. Notifications
**Email — automatic via SMTP.** **Scheduled reminders** run at **09:00 Asia/Kolkata**: subscription expiry reminder **15 days before the expiry date**; overdue reminders on the **due date, day 3 and day 7** (days counted after the due date); subscription expiry notice. **Immediate notifications:** subscription activation, payment receipt, loan issue, loan renewal, book return and token forfeiture — the day-8 forfeiture notification is sent **immediately after forfeiture processing**. **SMTP retries:** the initial email is sent immediately; **retry 1 is 5 minutes after the initial failure, retry 2 is 30 minutes after retry 1 fails, retry 3 is 2 hours after retry 2 fails** (each delay runs from the preceding failed attempt, not cumulatively from the first failure). After the third retry fails the notification is marked **failed** and the error details are retained; there is no further retrying. Retries reuse the same notification record, so they never create duplicate emails; the same event never produces more than one email (duplicate prevention). A member with no email address is recorded as **skipped with the reason `no email address`**. Statuses: Prepared, SMTP accepted, SMTP failed, Skipped; SMTP accepted ≠ delivered or read. All scheduled times are in Asia/Kolkata. Duplicate prevention by `dedupe_key` (member + event + occurrence); retry state (`attempt_count`, `next_retry_at`) lives on the same `NotificationLog` row. Failed emails appear on the dashboard. **WhatsApp — manual:** the app builds a prefilled `wa.me` message for the selected member's E.164 number; the owner reviews and sends; the owner may mark "Marked sent". Templates use restricted placeholder substitution (not Django templates).

## 12. Dashboard
Default sections: overdue books, upcoming subscription expiries, backup failures, failed emails, damaged/lost decisions, token forfeitures, members requiring attention. **No Pending Payments section.** Owner configures section visibility and the criteria of "Members requiring attention" (stored in `DashboardPreference`). Default criteria: expired subscriptions; borrowing suspended after token forfeiture; overdue books; unresolved damaged/lost cases; pending owner decisions; incomplete membership records.. Monthly collections show all receipts with subscription fees, token collections and other transactions separately.

## 13. Reports and export
Reports: members and subscriptions, subscription collections (payment date), subscription revenue allocation, token collections/refunds/forfeitures, adjustments, loans/overdue, damaged/lost, inventory/circulation, member history. Allocation is daily pro-rata computed at **full precision at report time**; rounded only for display; per-day rounded amounts are never stored. Outputs CSV/XLSX/PDF with formula-injection escaping. Full export = ZIP (CSV + Excel + manifest).

## 18. Database roles and privileges (L6, implemented)
Full detail: `docs/DATABASE_SECURITY.md`. Code: `core/dbsecurity.py`, `core/checks.py`, `core/management/commands/{migrate,apply_db_grants,check_db_security}.py`, `config/settings/migrate.py`, `deploy/postgres/*.sql`.

- **Roles.** `postgres`: break-glass superuser, not used by the application or scheduled jobs. `coven_owner`: owns the database and every object, runs migrations, grants and restores, manages `btree_gist`; NOSUPERUSER, NOCREATEROLE (CREATEDB only on development machines for the test suite). `coven_app`: runtime role (NOSUPERUSER, NOCREATEDB, NOCREATEROLE; no CREATE on the schema, no TEMP).
- **Classification.** Every table has an explicit class: MUTABLE (SELECT/INSERT/UPDATE/DELETE), NO_DELETE (SELECT/INSERT/UPDATE), APPEND_ONLY (SELECT/INSERT), READ_ONLY (SELECT; Django framework tables). TRUNCATE, REFERENCES and TRIGGER are never granted; sequences get USAGE+SELECT (SELECT only for READ_ONLY tables).
- **Fail closed.** `ALTER DEFAULT PRIVILEGES` is used only to REVOKE default privileges for the runtime role; no privilege is ever granted automatically. A table missing from the registry receives no runtime privileges and fails the check (`coven.E001`, system check `database_security`, start-up assertion in `wsgi`/`asgi`). Grants are reapplied explicitly and idempotently after every `migrate` (post_migrate hook) and by `apply_db_grants`.
- **Migrations.** Run only with owner credentials: `migrate --settings=config.settings.migrate`. The `migrate` command refuses to run as the runtime role. Owner credentials (`DB_OWNER_USER`, `DB_OWNER_PASSWORD`) come from a separate git-ignored `.env.owner` and are read only by the migrate and test settings; production settings never read them. `DB_SECURITY_MODE=strict` is the default; `single_role_dev` is development/test only and production refuses it.
- **Runtime restrictions.** `coven_app` cannot change schema, create or alter tables, alter or drop triggers, replace trigger functions, change ownership, grant privileges, create extensions, UPDATE/DELETE append-only tables, DELETE from no-delete tables, or TRUNCATE anything. Existing append-only triggers are unchanged; trigger functions pin `search_path = pg_catalog`.
- **Backup/restore.** `pg_dump -Fc` works as `coven_app`. Restore: provision roles first, restore as `coven_owner` into a database it owns, then run `apply_db_grants` and `check_db_security` as both roles. Restoring never relies on dumped ACLs.
- **Verification status.** Verified on macOS with PostgreSQL 16.15: 266 tests (suite as `coven_owner`, privilege tests as `coven_app`), rollback/forward migrations, disposable-database backup/restore. **Not verified:** Windows 11, the Dell, PowerShell provisioning, Task Scheduler with runtime credentials, and any clean-machine recovery (Phases 7b/7c).
- **Limits.** A PostgreSQL superuser or an OS administrator can bypass all of this. `.env.owner` is plaintext: keep it mode 0600, git-ignored, off backups and cloud-synced folders, and on the Dell present only during upgrades. Owner can drop triggers, so owner use is limited to migrations and restores.

## 19. Phase 3: subscriptions, finance and tokens (implemented)
Code: `memberships/` (policy, services, plans, subscriptions), `finance/` (ledger, tokens, corrections, receipts, allocation, reporting). Allowed imports hold: `memberships -> finance, members`; `finance -> members, audit, core`.

- **Date policy.** `memberships/policy.py` is the only place with date arithmetic (pure, `today` injected): calendar-month addition with end-of-month clamping, `expires_on` = first expired day, last valid day = expiry - 1, `next_start` (early renewal = current expiry; late = owner-entered activation date; one scheduled maximum; no overlap), the final-15-day issue block and the due-date cap as independent checks, and the loan-renewal check. Database backstop: an exclusion constraint on non-cancelled periods per member (`btree_gist`, created by the owner role in migration `memberships.0002`).
- **Ledger.** `finance.services.post_items` is the only writer. It validates exact settlement (split cash/UPI must equal the amount: no partial or excess payment), dates and backdating (any past date: reason plus extra confirmation), allocates receipt numbers, builds one immutable `ReceiptDocument` snapshot (a combined registration printout lists both receipts), then inserts transactions and payment entries. All six ledger tables are APPEND_ONLY (triggers + SELECT/INSERT only). No subscription-fee refund kind exists (CHECK on `kind`).
- **Receipt numbers.** Four per-year sequences (`SUB`, `TOK`, `REF`, `ADJ`) from `IdSequence` rows locked inside the posting transaction; the year is the issuance (today, Asia/Kolkata) year, never the backdated payment year; a rolled-back operation leaves no gap. Forfeitures and reversals have a UUID and no receipt.
- **Locking and idempotency.** Every operation locks the member row first (`SELECT ... FOR UPDATE`, allowed because members is NO_DELETE), then the sequence rows, so concurrent operations serialise without deadlock. Append-only tables are never locked. An optional `request_key` (hidden form field, one UUID per form, derived per record) makes a double submission post once.
- **Tokens.** `finance.tokens` derives the state of the latest cycle from the immutable ledger. One collection, refund and forfeiture per cycle (partial unique indexes); a deferred trigger keeps the cycle balance within 0..amount. A fresh token starts a new cycle for the same member and never touches subscriptions. A held token is carried across renewals by a zero-value `carry_forward` entry.
- **Operations (atomic).** `register_member`, `renew_subscription`, `pay_fresh_token`, `cancel_subscription` (memberships) and `refund_token`, `forfeit_token`, `reverse_transaction`, `post_adjustment` (finance.corrections). `forfeit_token` and the `OUTSTANDING_LOAN_CHECKS` / `borrowing_blockers` hooks are ready for Phase 4 but not wired to loans.
- **Allocation and reports.** `finance.allocation` uses exact fractions (daily pro-rata, no stored per-day amounts, rounding only in `display_rupees`); `finance.reporting.collections` keeps subscription fees, token collections, refunds, adjustments, reversals and forfeitures apart. Report screens arrive in Phase 6.
- **Receipts.** HTML (print stylesheet) and PDF (ReportLab, already a dependency) are rendered from the snapshot; the member name is shown live.
- **Owner decisions:** D-7 to D-14 and D-16 are decided and D-15 is approved (implementation deferred to Phase 4b); none is awaiting confirmation. Status and evidence: OPEN_QUESTIONS section 3 and 19.1 below. Open items: Phase 6 must list unlinked cash-out adjustments separately (D-7), D-14 plan editing is deferred to the settings phase, and Windows 11 / clean-machine recovery / a real-browser check are unverified.

### 19.1 Remediation after the Phase 3 review (owner decisions D-7 to D-14)
- **64-bit money, limits (H1, D-16).** All paise columns stay 64-bit, each with a CHECK of at most `core.money.MAX_PAISE` = 4,999,900 paise (Rs 49,999.00, owner decision D-16). `core.money.check_amount` validates in services (`amount_too_large` / `amount_invalid`), the form fields use `MAX_RUPEES`, and the database refuses anything larger, so an oversized value is always a validation error and never a database error. The same limit applies to book unit costs (manual and Excel import).
- **Reasons (H3, D-16).** `core.money.clean_reason` rejects (never truncates) text above `MAX_REASON_LENGTH` = 2,000 characters for every reason and note: adjustments, reversals, forfeitures, backdating, subscription cancellation and anonymisation. Forms enforce the same maximum.
- **Backdating audit (H2).** `finance.services.audit_dates` adds to every finance and membership audit summary: `backdated`, `effective_date`, `processed_at`, and, when backdated, `backdate_reason` and `backdate_owner_confirmed`; registrations and renewals also record the non-financial `event_date` (subscription start) and `event_date_backdated`, so a past start date with a payment made today is still audited.
- **Corrections (D-7, final).** `post_adjustment` requires a mandatory reason, the owner's approval and, for money out, `confirm_not_fee_refund`; it refuses money out against a subscription payment. An unlinked cash-out adjustment is a permitted, explicitly owner-approved accounting correction: it records owner (`recorded_by`), timestamp (`processed_at`), amount and the audit event with the confirmation, and must be listed separately in the Phase 6 reports (`kind=adjustment`, `cash_flow=out`, no `adjusts` link), never as a fee refund. The database cannot see the confirmation; trigger `finance_txn_correction_rules` (BEFORE INSERT, fixed `search_path`) enforces the same rule and the no-reversal rule for subscription payments, token refunds and reversals even for direct SQL.
- **Anonymisation (H5, D-12).** `anonymise_member` is atomic and locks the member row first, like every payment, token and subscription operation, then works on the fresh row. Eligibility is unchanged by anonymisation: only the full token refund remains possible.
- **System actor (H4; D-15 APPROVED, implementation deferred to Phase 4b).** `recorded_by` is required today and the single-owner constraint forbids a second user row, so no system user is created. Approved design: an optional `recorded_by_system` attribution valid **only** for the automatic day-8 forfeiture (`overdue_auto`); database CHECKs make exactly one of owner/system attribution mandatory and refuse the system actor on any other kind or trigger; audit events for it have an empty actor and `summary.system`; the launch catch-up uses the same actor (effective date day 8, real processing timestamp); manual owner actions always keep the authenticated owner; the system actor is not a general attribution bypass. Nothing of this exists in Phase 3.

## 20. Phase 4: circulation (implemented)
Code: `circulation/` (`services` issue / return / lost / renew, `forfeiture` day-8 rules and the daily job, `grace` grace changes and owner decisions, `events`), loan date arithmetic in `memberships/policy.py`. Allowed imports hold: `circulation -> members, catalogue, memberships, finance, core, audit`; `catalogue` refers to `circulation.Loan` only by a string foreign key.

- **Issue.** Locks member then copy (the same order everywhere), then checks: member status, subscription valid on the issue date, held token, no book outstanding, copy Good + Available, then the final-N-day block and the due-date cap (independent) against the member's contiguous coverage (`policy.coverage_period`). Partial unique indexes enforce one active loan per member and per copy; a guard trigger freezes issue facts and closed loans.
- **Outcomes.** Good returns the copy to Available. Poor = condition Poor + status Withdrawn; Damaged = condition and status Damaged; Lost = condition and status Lost and the loan closes as Lost. Poor / Damaged / Lost need the owner's confirmation and a mandatory reason, and forfeit the full token (owner attribution, effective date = the return or loss date). Withdrawn stays a separate status (condition Good, set by the owner).
- **Automatic day-8 forfeiture.** `forfeiture.apply_automatic` posts the full token (`overdue_auto`) when the reference day (today, or the return date of a closed loan) reaches due + grace + 1. It is attributed to the restricted system actor `overdue_forfeiture_job` (decision D-15; no user is created, the single-owner constraint is untouched; `finance_ledger_attribution` forbids any other use), keeps the original effective date when processed late, and is idempotent (one forfeiture per token cycle, `loan.forfeiture_entry` set once). A loan awaiting or refused in an owner decision is skipped.
- **Daily job.** `python manage.py run_daily_jobs` (`forfeiture.process_overdue_forfeitures`): one transaction per loan, locking member, setting and loan in the same order as every other operation. Task Scheduler and launch wiring: Phase 7c.
- **Grace changes.** `grace.change_grace_days` locks the setting, records a `SettingChangeEvent` listing the loans that become newly eligible, creates a `PendingForfeiture` for each and changes the setting. `confirm_pending` posts the forfeiture (owner, mandatory reason); `decline_pending` needs a reason and is final.
- **Notification outbox (D-23, implemented: durable storage only).** `core.outbox.emit()` inserts a `core_domainevent` row inside the caller's open transaction (RuntimeError outside one): rollback leaves no event, commit leaves it, a repeated key creates no duplicate (unique `dedupe_key`, savepoint + IntegrityError). On a repeated key `emit` loads the stored event and compares event type, member reference and payload (canonical JSON, so key order is irrelevant): identical returns `False` and adds no row; any difference raises `core.outbox.OutboxKeyConflict`, which rolls back the surrounding business transaction. The stored event is never updated or replaced. Columns: `event_id` (UUID), `dedupe_key`, `event_type`, `member_id` (no FK), minimal JSON `payload`, `event_date` (business date, Asia/Kolkata), `occurred_at` (original timestamp, e.g. the real processing time of a late day-8 forfeiture), `created_at`. APPEND_ONLY (trigger `core_domainevent_append_only`, `coven_app` has INSERT + SELECT only). Payload keys that could hold names, contact details, free text, reasons or credentials are refused. Event types: `member.registered`, `subscription.activated`, `subscription.renewed`, `payment.receipted` (one per receipt document, so a combined registration printout is one event), `token.collected`, `token.refunded`, `token.forfeited` (central in `finance.corrections.forfeit_token`: automatic, owner-confirmed and grace-confirmed, with `system` true for the day-8 job), `loan.issued`, `loan.renewed`, `loan.returned` (outcome good/poor/damaged), `loan.lost`. The old in-memory `circulation.events` is deleted and tested as gone.
- **What outbox events mean.** Events are business facts, not delivery state. `payment.receipted` means only that a receipt document was issued; it does not mean an email was sent, delivered or read. Pending, skipped, failed, sent and retry states belong to Phase 5b notification records and never to the outbox. Payloads never contain recipient email addresses or other unnecessary personal data. Phase 5b resolves the recipient's current email from the member record using `member_id` when it processes an event, and the notification record must retain the address actually used for delivery. If anonymisation has removed the address, the notification is skipped with a recorded reason.
- **Phase 5b contract (implemented in section 21; this text is the original contract).** A worker reads events with no notification record, creates one notification row per event keyed by `dedupe_key` (unique), and keeps pending / skipped (missing email, with reason) / failed / retry state ONLY in the notification table; events are never updated or deleted and are retained permanently. The SMTP schedule is the approved one (immediate; retry 1 after 5 minutes, retry 2 after 30 minutes, retry 3 after 2 hours, each from the preceding failed attempt; then failed, no further retries), reusing the same notification record, so no duplicate emails. Concurrent workers must claim rows atomically (`SELECT ... FOR UPDATE SKIP LOCKED` on the notification row, or an insert-on-conflict claim) and be idempotent; an interrupted worker is recovered by rescanning for unconsumed events and stale claims. Scheduled expiry and overdue reminders (09:00) are Phase 5b logic; running the worker and `run_daily_jobs` unattended is Phase 7c (D-24).
- **Concurrency.** Tests run real parallel connections: copy and member races, double returns, issue versus token refund, job versus job, job versus a day-8 return, renewal versus return, grace change versus job, confirm versus decline.



## 21. Phase 5: dashboard and notifications (implemented)
**5a (core).** `core/dashboard_config.py` validates the owner's configuration (stored in `LibrarySetting.dashboard_config`, JSON; unknown or bad values fall back to defaults). `core/dashboard.py` only READS other apps (imports are inside functions; `core` keeps no import-time dependency on them). Pages: `/` (sections in the owner's order), `/search/`, `/calendar/`, `/settings/` (visibility, up/down order, attention criteria, expiry window). Migration `core.0009`. Defaults and interpretations: OPEN_QUESTIONS D-25.

**5b (`communications` app).** Tables `communications_notification` (NO_DELETE, guard trigger), `communications_notificationattempt` (APPEND_ONLY) and `communications_messagetemplate` (MUTABLE); migrations `communications.0001-0002`.
- **Delivery state lives only in `Notification`.** `dedupe_key` is unique and equals the outbox event key (or `reminder:...`), so one event or reminder can never create two records or two emails; retries reuse the row. Status: Prepared, SMTP accepted (never "delivered"), SMTP failed (will retry), Failed (retries used up), Skipped (code + reason: no email address / member anonymised / no email defined). Every attempt is an append-only `NotificationAttempt` with the address used and the error.
- **Outbox consumption** (`communications.services.consume_events`): an event is consumed when a notification with its `dedupe_key` exists. The recipient email is resolved from the member by `member_id` at processing time and stored on the notification; payloads never hold addresses. Interrupted runs simply continue; concurrent consumers are safe because the unique key rejects the loser.
- **Sending** (`send_due`): due records are leased with `SELECT ... FOR UPDATE SKIP LOCKED` (10-minute lease, claim token); SMTP is called outside any database transaction; the result is recorded in a second transaction that requires the same claim token, so a worker whose lease was taken over records nothing. The address is re-resolved before every attempt: an anonymised member or a removed address stops the email (skipped). Errors are stored with SMTP credentials and the recipient address scrubbed.
- **Retry schedule (approved):** initial immediately; retry 1 five minutes after the initial failure; retry 2 thirty minutes after retry 1 fails; retry 3 two hours after retry 2 fails (each from the preceding failed attempt, not cumulative); then `failed`, error kept, no automatic retry. At most 4 attempts (a CHECK enforces it); the guard trigger forbids leaving a finished state, returning to Prepared, lowering the attempt count or changing identity.
- **Reminders** (`due_reminders` / `schedule_reminders`): due from 09:00 Asia/Kolkata (the clock is Asia/Kolkata, not UTC): expiry reminder 15 days before expiry, expiry notice on the expiry date, overdue reminders on the due date, day 3 and day 7. **Back-fill (D-27a):** a missed reminder is created on the next run for up to 7 days, only while still relevant (expiry reminder: not expired or renewed; expiry notice: member still uncovered; overdue: loan still out and before day 8, latest missed milestone only). `Notification.scheduled_for` keeps the original date, `created_at` the real processing time; the unique key prevents duplicates. The day-8 forfeiture notice is the `token.forfeited` event and is sent in the same `run_daily_jobs` run, immediately after forfeiture processing.
- **Anonymisation (D-27b).** `members.services.ANONYMISATION_HOOKS` runs `communications.services.redact_member_notifications` INSIDE the anonymisation transaction (a failure rolls the anonymisation back; audited as `notifications.redacted`): prepared and retry-pending -> skipped and erased; failed -> skipped and erased; SMTP-accepted -> subject and body erased, address and time kept 90 days from anonymisation, then `redact_expired_addresses` (part of every cycle) erases the address. Errors keep their type only, and `NotificationAttempt` stores no address, so the append-only log never needs rewriting. The hook receives the authenticated owner and the redaction audit entry names that actor (no personal data in the entry). A message already in flight when the anonymisation commits cannot be recalled, but its claim is cleared, so its outcome is not recorded, no attempt row is written, nothing restores the erased content and no automatic resend follows (proved by a deterministic two-thread PostgreSQL test). The 90-day address retention is a database-assisted floor, not tamper-proof retention (R-55). Deployment safeguards for existing data: migration guard and `preflight_notifications` (DATABASE_SECURITY, "Phase 5 deployment safeguards").
- **Triggering.** `communications.middleware.NotifyAfterWriteMiddleware` runs a cycle after a successful owner POST (best effort; a failure is logged and never affects the response; `NOTIFY_AFTER_WRITE=false` disables it). `run_daily_jobs` (still run by hand until Phase 7c) and the "Process now" button run the same cycle. **Phase 7c** owns unattended scheduling.
- **WhatsApp stays manual.** `/reminders/whatsapp/<member>/` renders an editable template (a fixed placeholder whitelist; nothing is evaluated) and a `https://wa.me/<number>?text=...` link that opens in a new tab for the owner to review and send. No WhatsApp API or library is used and nothing is sent by the application (tested).
- **SMTP** settings come from the environment (`EMAIL_*`, placeholders in `.env.example`; `EMAIL_TIMEOUT` 15 s). A "Send test email" action sends to the owner account's address and reports SMTP acceptance honestly.
- **Windows 11:** unverified. Only the standard library SMTP client is used; nothing is OS-specific.


## 22. Phase 6: reports and exports (implemented)
App `reports` (no tables, no migrations; read-only queries). `reports/periods.py` (calendar presets, D-28a), `reports/queries.py` (nine reports), `reports/statement.py`, `reports/export.py`, `reports/render.py`, `reports/core.py` (`Report` / `Section` / `Column`; money cells hold EXACT paise or Fractions).
- **Two revenue bases, never mixed.** Collections use each payment entry's own `paid_on`; tokens, refunds, forfeitures (by effective date, no cash), adjustments and reversals are separate lines. Allocation spreads each fee over its valid days with exact rational arithmetic (`finance.allocation`), includes cancelled subscriptions (D-13) and excludes tokens. Rounding happens once per displayed value and per total, half-up (D-28e), with a printed note.
- **D-7 (5).** The adjustments report puts unlinked cash-out adjustments in their own section.
- **Outputs.** HTML, CSV (UTF-8 with BOM), XLSX (openpyxl) for every report; PDF (reportlab) for the collections and allocation reports and the member statement (D-28b). Every text cell is escaped against formula injection (leading `= + - @`, tab, CR get an apostrophe; XLSX strings are also typed as strings); money and numbers are never escaped.
- **Full export.** `POST /reports/export/` builds a ZIP in memory (not stored): one CSV per record type, `coven_export.xlsx` (a sheet per type) and `manifest.json` (counts, SHA-256, exclusions). Amounts are integer paise. A test enforces that every model is exported or named in `NOT_EXPORTED` with a reason, so a new table forces a decision. No message text, addresses, audit summaries or receipt snapshots.
- **Escaping and masking (D-28h to D-28k).** `core/spreadsheet.safe_text` (the single implementation, also used by the catalogue import error report; `reports/render` re-exports it) escapes after skipping leading whitespace and control characters and exempts only a strict phone number; `reports/masking.py` masks member-linked free text for anonymised members in every report, statement and export (`export.DATASETS` carries a per-dataset mask spec); payment-entry references are masked as well; donor names are excluded from exports (they are stored but not displayed anywhere in the application); XLSX shows illegal control characters as control pictures.
- **Access.** Every view needs the owner login; exports are POST (CSRF) or audited GETs; each export writes an audit event with the format, range and row count only.
